topic: Atari NIO over physical SIO

- (direction by user) Deliver Atari as a first-class FujiNet-NIO target beside BBC, Amiga, and MS-DOS; this is the primary goal.
- (constraint by user) Legacy transport, legacy framing, and compatibility with old FujiNet Atari software are out of scope and must not influence the design.
- (decision by user) Atari uses standard FujiBus application protocol with SLIP framing over a physical Atari SIO channel.
- (capability) CAP-1: define and share the Atari NIO SIO channel contract across the Atari client, ESP32 firmware, NetSIO, AltirraSDL, and independent wire fixtures.
- (capability) CAP-2: make the fujinet-nio-lib Atari backend a supported public-API transport, with an Atari guest acceptance program.
- (capability) CAP-3: make the official FujiNet v1 ESP32 physical SIO profile a supported NIO deployment with timing, buffering, recovery, and board acceptance evidence.
- (capability) CAP-4: run shared Atari NIO acceptance fixtures through AltirraSDL and NetSIO as protocol regression environments, not physical-hardware proof.
- (capability) CAP-5: provide a documented real-Atari/operator acceptance procedure covering flash, diagnose, standard NIO service calls, and recoverable failures.
- (assumption) Configured project-context.md is absent; the contract uses the inspected architecture, build, client, emulator, and workspace instructions as its evidence base.

- (decision) Freeze SIO device ID 0x7F as the fixed Atari NIO channel address; it selects only the SIO W/R byte-pipe envelope, never a FujiBus service, and an address collision reports NIO unavailable with no fallback, discovery, or legacy behavior.
- (decision) Supersede the initial SLIP direction: Atari NIO SIO carries packet-native FujiBus request and response packets; SIO transaction boundaries, not SLIP delimiters, define packet boundaries. Do not add SLIP escaping or a stream transport to the Atari path.
- (decision) Set the initial maximum packet-native SIO payload to 1024 bytes for both W requests and R responses, defined by one shared named compile-time contract constant so builds and performance experiments may change it together. AUX carries the exact SIO payload length; a FujiBus packet exceeding the configured limit fails with a defined NIO message-too-large transport error and is never implicitly segmented.
- (decision) Supersede the initial 1024-byte limit: set the initial maximum packet-native SIO payload to 512 bytes for both W requests and R responses, defined by one shared named compile-time contract constant so builds and performance experiments may change it together. W and R carry exact payload length in AUX and matching DCB byte count; a FujiBus packet exceeding the configured limit fails with a defined NIO message-too-large transport error and is never implicitly segmented.
- (decision) Add NIO-only P polling at SIO device 0x7F: a valid P always returns ACK, COMPLETE, and a fixed three-byte status payload of state (idle, pending, ready, or fault) plus little-endian queued response size. The client polls P, then sends R with that exact size only when ready. NAK remains reserved for malformed/rejected transport transactions, never means pending.
- (decision) Make PROC an opt-in NIO readiness notification. The library is polling-only by default and never installs, replaces, or silently owns an Atari IRQ/VPRCED handler. An application that owns/chains its handler may call an ISR-safe constant-time library notification hook that only latches a flag; outside IRQ context the library/application confirms readiness and size with P before R. The board emits a bounded, rate-limited PROC pulse only when its NIO response queue becomes ready; no source, request ID, or reason is encoded on the shared line, and a missed or false pulse is harmless because the queue remains until fetched/reset and polling remains correct.
- (constraint) Atari NIO v1 physically requires CMD and UART data input/output at standard 19,200 baud. Board-driven data output and PROC use released-idle open-drain behavior. INT, MTR, CKI, and CKO have no NIO protocol semantics and must remain electrically benign. Physical acceptance measures logic levels, no contention, command-to-control timing, data/checksum timing, abort/reset recovery, and both PROC opt-in and polling-only behavior; it makes no high-speed claim.
- (decision) Require Clock, Network, File, and Disk as the mandatory real-Atari Atari NIO service acceptance set. Clock proves a small deterministic exchange; Network proves open/write/read/close with a delayed readiness path; File proves persistent write/read; Disk proves read and write against an already-mounted supported image. Disk acceptance uses the established service/media workflow and does not reopen disk-media design.
- (direction) Atari FujiNet-NIO must act as the user's D: drive as well as the NIO application peripheral: a stock Atari boots from D1 over SIO, and the product must serve URI-backed ATR images as D1, D2, and subsequent units through the established disk-slot and boot-mode model.
- (decision) Define two deliberately separate Atari SIO ingress planes on the same official FujiNet hardware: (1) NIO application channel at device 0x7F with packet-native FujiBus W/P/R, and (2) standard Atari disk frontend at D1-D8 device IDs for OS boot and mounted ATR sector I/O. The disk frontend translates only standard Atari disk transactions into internal IORequest/IOResponse operations for the existing DiskDevice/DiskService, then encodes standard sector replies; it never exposes FujiBus framing to the Atari OS.
- (constraint) The required Atari disk frontend is not LegacyTransport and must not reuse or expand legacy FujiNet service adapters, device mappings, configuration commands, N:, R:, or proprietary framing. It is a purpose-built D: bootstrap/media adapter limited to standard Atari disk semantics and isolated from the 0x7F NIO channel except for shared physical SIO, disk slots, and DiskDevice service contract.
- (decision) Atari startup uses the existing boot configuration policy: config mode mounts the flashed Atari configuration/boot ATR URI as the D1 candidate; normal mode restores user-selected URI-backed D1-D8 slots. The disk frontend supplies the selected D1 image during OS boot. The configuration ATR contains the cc65 XEX acceptance/config applications, so no separate non-FujiNet loader is required.
